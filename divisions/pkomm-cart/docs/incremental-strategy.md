# Incremental Strategy

## The problem
In a real store, records change after they first show up:
- Orders move through statuses (PLACED → SHIPPED → DELIVERED)
- Payments fail first and go through later
- Shipments update as packages move

Reloading all history every day is slow and gets slower. Loading only today's new rows gets the past wrong. So each layer has its own rule.

## What the source sends
Each day's folder holds only what was new or changed that day. To decide what can change, the generator rebuilds the store's current state from every earlier day's files and keeps the newest version of each record. Late changes only reach orders, payments and shipments created in the last 7 days, and never touch delivered or cancelled orders. Each day has its own seed, so a day can be regenerated byte for byte.

## Bronze: keep everything, but only once
- Every file is loaded as it arrived, with `batch_date`, `ingested_at` and `source_file`.
- Across days it only grows. Nothing is updated or deduplicated.
- Loading a day again first deletes that day's rows, so a rerun replaces the day instead of doubling it.

## Silver: one row per key, newest wins
### Upsert tables (customers, products, orders, payments, shipments)
- Insert if the key is new
- Replace if the key exists and the incoming `updated_at` is newer
- Ignore if the incoming `updated_at` is older or equal

### Append-only table (order_items)
- Insert new line items only. Items never change after an order is placed.

Only the keys that are new or newer are replaced: a delete and insert of just those keys, inside one transaction. If anything fails, silver stays as it was. Every run writes what it received, inserted and updated to `pipeline_merge_log`, so a rerun shows up as a run that changed nothing.

## Gold: rebuilt from silver
- `gold_fact_orders`: one row per order with its latest payment and shipping status.
- `gold_kpi_daily`: daily numbers by order date. `gross_revenue` only changes when new orders arrive for that date. `captured_revenue` changes whenever a late payment lands, which is exactly the number finance saw moving.
- `gold_kpi_history`: the daily numbers as they looked after every run, so you can watch a past day settle.
- Money is `DECIMAL(14,2)`, so reruns give the same totals to the cent.

## Known limits
- Gold is rebuilt from silver every run. At this size that's fine. At scale, only the order dates touched by the batch should be rebuilt.
- The DuckDB version pinned here has no `MERGE` statement, so the merge is a delete and insert in one transaction.
- Hard deletes from the source aren't handled. Cancellations arrive as status changes.
